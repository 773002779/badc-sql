## 0. 关键决策摘要（先看这 10 条）

这一版最容易被误读的地方是**谁能执行**，先说清楚。系统里有**三条执行路径**，不要混：

1. **研发：只读自助 + 工单触发。** 研发对**只读库**可自助查询；对写库**不能**直接执行任何语句（接口 403）；变更走工单，**审批通过后研发可以自己点"执行"触发**。
2. **运维：临时执行通道。** 运维对只读库和写库都可直接执行；L1/L2 弹框自确认即可执行（默认自己同意），**L3 弹框后自动生成工单，交组长一级审批**。
3. **审批深度**：研发工单 **L1/L2 运维一级、L3 运维 + 组长两级**；运维临时执行 **最多一级**（仅 L3）。
3b. **不用四眼原则**：运维执行不设第二人复核、不做大表二次确认，安全网是**结构快照 + 必填回滚 SQL + 全量审计**。
4. **研发不碰数据库凭证**：界面只显示库名，连接串仅运维可见；执行时代跑的是平台配置的服务账号，审计同时记"操作人"和"执行身份"。
5. **一个库只属于一个系统**，不做跨系统共享授权。
6. **只纳管生产库**，测试/预发不进平台，也就不做 `env` 维度。
7. **变更前只抓表结构快照，不备份行数据**（数据量太大），快照存本地磁盘。代价是 DML **没有数据级回滚**，靠提单人写的回滚 SQL 或云厂商 binlog 恢复。
8. **数据库是云托管**，MySQL 5.7 与 8.0 并存 → 所有能力必须**运行时探测**，5.7 没有的特性在 UI 上直接隐藏。
9. **非窗口期执行，风险等级自动 +1 级**——不做硬性时间拦截，用升级审批来替代。
10. **一期按"控制面 + 执行器"分层**，虽然现在是 K8s 单机房，但为后期多云统一前端预留，不返工。

## 1. 背景与目标

### 1.1 现状

研发修改线上数据依赖 DBA/运维手工执行或直连生产库，存在：

- 无统一入口，SQL 散落在聊天记录、文档、临时脚本里，事后无从追溯；
- 高风险语句（`drop` / `truncate` / 大范围 `update` / `alter`）缺少强制拦截与二次确认；
- 变更前没有结构快照与强制回滚方案，误操作只能靠云厂商的实例级备份做时间点恢复，RTO 以小时计；
- 研发没有自助查数通道，任何查数都要找人，运维被打断；
- MySQL 5.7 / 8.0 双版本并存，很多"标准做法"在 5.7 上不成立。

### 1.2 目标

建设**生产库写操作的唯一入口**，把"查数 / 改数 / 改结构"收敛到一个平台：

| 目标 | 落点 |
|---|---|
| 可控 | 研发无法对写库直接执行任何语句，写操作只能经由已审批工单；运维临时执行留痕；写操作 100% 经平台 |
| 可逆 | 变更前留存**表结构快照**（不含数据），配合**必填回滚 SQL** 与云厂商 binlog 实现可追可退 |
| 可审 | 全链路 append-only 审计，谁提交、谁审、谁执行、影响多少行，一条链可查 |
| 可自助 | 研发查数、看表结构自助完成，小额导出自助完成 |

### 1.3 非目标

- 不做数据库监控/告警/慢查询采集（归监控体系）；
- 不做数据同步/迁移；
- 一期不做查询结果脱敏（Q-13 明确不做），仅做角色维度的可见性控制；
- 不做 SQL 自动改写（性能分析只给建议）；
- 不做多租户 SaaS；
- 不纳管测试/预发库（Q-22），平台外直连测试库是已知且接受的现状。

### 1.4 成功标准

| 指标 | 目标 |
|---|---|
| 生产写操作平台覆盖率 | 100%（无平台外手工执行） |
| 变更事故（误删/误改）次数 | 相比现状下降 ≥ 80% |
| 变更的回滚方案覆盖率 | 100% 变更工单在提交时即带回滚 SQL/回滚方案 |
| 研发查数自助率 | ≥ 90% |
| L1/L2 工单平均审批时长 | ≤ 2 小时（工作时间） |
| L3 工单平均审批时长 | ≤ 1 个工作日 |

## 3. 术语

| 术语 | 定义 |
|---|---|
| 系统（System） | 业务系统，如"订单中心"。权限、运维归属的最小单位 |
| 功能模块（Module） | 系统下的业务模块，如"订单查询"。研发授权的最小单位 |
| 数据源（Data Source） | 一个云实例 + 一个库名（含连接串、账号集）。**一个数据源只归属一个系统** |
| 实例（Instance） | 云上数据库实例，一个实例可含多个库 |
| 语句（Statement） | 待执行的最小单元。MySQL/PG 为单条 SQL；MongoDB 为单个 `db.*` 调用 |
| 工单（Ticket） | 一次审批请求，含 N 条语句，归属一个系统 + 模块 + 一种数据源类型 |
| 变更（Change） | 工单中一条语句在某数据源上的一次实际执行 |
| 结构快照（Snapshot） | 变更前留存的表结构定义（列/索引/约束/触发器/分区），**不含行数据** |
| 临时执行通道 | 不建工单、直接在编辑器执行语句的通道。**研发**只能对只读库执行 `select`；**运维/组长**可对读写库执行 DML/DDL（L1/L2 自确认，L3 转组长审批） |
| 工单执行 | 研发提交的工单经审批通过后，由**研发本人或运维**点击触发的执行 |
| 执行窗口 | 允许执行 L2/L3 变更的时间段，由主运维维护 |

### 4.3 硬性约束（服务端强制，不可配置绕过）

1. **研发的写路径只有工单**：研发调用"临时执行写语句"接口一律 403（接口级拒绝，不是藏按钮）。研发能执行的只有两类——对只读库的 `select`，以及**已审批工单内的固定语句**。工单执行时不允许改语句、追加语句、换数据源。
2. **研发工单无自审**：`提交人 ≠ 审核人`；L1/L2 审核人必须是运维，**L3 再加组长终审**，两级不可同一人。
3. **运维临时执行不使用四眼原则**：L1/L2 由执行人自己确认风险即执行（默认自己同意）；**L3 由组长审批**。不设第二人复核、不做大表二次确认——安全网是结构快照与审计，不是层层签字。
4. **组长终审不可被代理**：组长请假时，由管理员临时授予另一名组长该系统的终审权，并留审计。
5. **管理员不可执行生产语句**：只能配置和授权。这是防止超级权限滥用的硬隔离。
6. **研发不可见连接信息**：研发侧的接口响应中，数据源仅返回 `{id, name, dbName, systemId, type}`，不含 host/port/user/密码/连接串。
7. **权限即时生效**：授权变更实时生效，不做 token 缓存；权限被回收后，正在执行中的工单在下一语句前中止。
8. **最小可见**：研发只能看到已授权模块下的数据源。未授权的库不在搜索、收藏、历史中返回（不是隐藏，是不查）。

### 4.4 授权与申请流程

```
① 建档（管理员）
   建系统 → 指定主运维 → 主运维配置模块、数据源、账号集、执行窗口

② 研发申请
   选 系统 → 模块 → 申请"查询/导出/提单"权限
   → 通知该系统主运维 + 备运维（企微应用消息 / 邮件）

③ 审批（主/备运维任一）
   通过 → 授予该模块下所有数据源的对应权限（只读）
   驳回 → 填理由，通知申请人

④ 运维横向
   运维可申请其他系统的"备运维"（需该系统主运维审批）
   主运维可直接配置他人为本系统备运维（被配置人确认）
   任何人不得给自己授予主运维（防自我提权）
```

### 4.5 临时执行通道（分两种身份）

不建工单、直接在编辑器里执行语句。**同一条通道，两种身份，权限不同**：

| | 研发 | 运维 / 组长 |
|---|---|---|
| 可连的库 | **仅只读库**（`readonly` 账号） | 只读库 + 写库（`readonly` / `dml` / `ddl` / `onlineddl`） |
| 可执行的语句 | 仅 `select` / `show` / `desc` / `explain` | 全部，含 DML/DDL |
| 是否记工单 | 否，只记查询历史 | 否（L3 除外），记 `DirectExecRecord` |
| 结构快照 | 不需要（只读不改变结构） | **强制执行**（L1 起，不可关闭） |

**研发侧规则**：

- 数据源统一用运维配置的**只读账号**，研发无法切换账号；
- 界面上库名可见、连接串不可见；
- 研发尝试 `insert`/`update`/`delete`/DDL → 接口 403 + 提示"请提交变更工单"；
- 研发在同一编辑器里对写库发起任何语句 → 直接拒绝（不是置灰，是后端拒绝）。

**运维侧规则（按风险分流）**：

| 语句风险 | 行为 |
|---|---|
| L0 只读 | 直接执行，记审计 |
| L1 低 | 弹框确认（含快照状态）→ 抓结构快照 → 执行 → 记 `DirectExecRecord` |
| L2 中 | 弹框展示风险详情（命中规则、影响行数、快照状态）→ 勾选确认 → 抓结构快照 → 执行 |
| L3 高 | 弹框提示"此操作需审批"→ 确认后**系统自动生成工单** → **交运维组长一级审批** → 通过后由该运维执行 |

**约束**：

1. **结构快照不可关闭**：运维临时执行 L1 起必须留下结构快照，这是变更基线的唯一来源；
2. **L3 不允许"先跑后补"**：自动生成的工单未经组长批准，语句不执行（语句暂存，不预先执行）；
3. **必须填"执行说明"**（≥10 字），用于事后追溯；
4. **同一数据源写并发 = 1**，有执行中任务时排队；
5. 所有临时执行在审计中打 `direct_exec=true` 标签，月度单独统计；
6. 研发的临时执行**不产生** `DirectExecRecord`，只产生查询历史。

> 与 v1.0 的差异：v1.0 曾要求运维 L3 由"另一名运维 + 组长"两审，现按需求方明确要求改为**组长一级审批**，因为执行人本身已是具备写权限的运维，自审被视为默认同意。研发工单的 L3 仍为两级（运维 + 组长）。

### 4.6 执行窗口（v1.0 新增）

- 窗口由**主运维按系统维护**（默认 `20:00–次日 06:00`，可配多段，支持按星期）；
- **窗口不做硬性拦截**，改为**风险升级**：非窗口期执行 L1/L2 时，风险等级自动 +1（L1→L2，L2→L3），从而触发更严格的审批；
- L3 在非窗口期执行 → 仍为 L3，但需组长终审时额外确认"同意在业务高峰执行"；
- 窗口配置变更留审计，并通知该系统研发（避免研发不知道什么时候能提单）。

### 4.7 组长的权限继承（v1.2 新增）

组长的权限**不是单独授权的**，而是由"组员"推导出来：

```
User(组长) ── 管辖 ──> User(运维 A) ── 主/备运维 ──> System X
                     └> User(运维 B) ── 备运维   ──> System Y

组长权限 = { X, Y } 的运维能力（含临时执行、L1/L2 审核）
         + { X, Y } 的 L3 终审权
         + { X, Y } 的 L3 临时执行审批权
```

**规则**：

1. 管理员只需维护"谁是谁的组员"，系统权限自动传递，不重复配置；
2. 组员在主/备运维上的任何变更（新增系统、被移除），组长权限**实时同步**；
3. 一个运维**可以**被多个组长管辖（如矩阵式管理）；
4. 一个系统**必须**至少被一名组长覆盖——系统建档时校验：若该系统的主/备运维都没有上级组长，**拒绝建档**并提示"请先为该运维指定组长，否则 L3 工单无人终审"；
5. 多个组长覆盖同一系统时，L3 终审为**或签**（任一组长审批即生效），并记录实际审批人；
6. 组长离职/转岗：其组员需重新挂到其他组长，未挂期间该系统 L3 **不可提交**（提交时直接拦截并提示），而不是让工单卡住；
7. 组长本人不因"管辖"而获得**研发**的任何权限——他只继承运维侧能力。

## 5. 组织与数据模型

### 5.1 层级

```
System（系统）
 ├── Module（功能模块）1..n
 │     └── 关联 DataSource（n..m，仅限本系统内）
 └── DataSource（数据源）1..n        ← 一库一系统，不跨系统共享
       ├── ConnAccount（readonly / dml / ddl / onlineddl）
       ├── ExecWindow（执行窗口）
       └── Capabilities（运行时探测结果）
```

**一库一系统的约束（Q-21）**：数据源有且仅有一个归属系统。若两个系统需要访问同一个库，由归属系统把该库的只读权限通过"模块"授予对方系统的研发——实现上仍是在本系统内建一个模块，把对方研发加进来。这比跨系统共享授权简单，代价是需要归属系统运维代为授权。

**只纳管生产（Q-22）**：不引入 `env` 维度，所有数据源默认 `prod`。若后期要纳管测试库，需在数据源上加 `env` 并重新定义策略继承（预留，不实现）。

### 5.3 状态机

```
Ticket:
  DRAFT ──提交(研发)──> REVIEWING_L1 ──通过──┬─ L1/L2 ─────────────> APPROVED
                              │              └─ L3 ──> REVIEWING_L2 ──通过──> APPROVED
                              └──驳回──> REJECTED                  └──驳回──> REJECTED
  APPROVED ──(研发点执行 / 运维点执行 / 定时到点)──> EXECUTING ──> SUCCEEDED | PARTIAL_FAILED | FAILED
  APPROVED ──超期(24h 未执行)──> EXPIRED
  * ──> CANCELLED

DirectExecTicket（运维 L3 自动生成，只有一级审批）:
  AUTO_CREATED ──组长通过──> APPROVED ──> EXECUTING ──> SUCCEEDED | FAILED
                └──组长驳回──> REJECTED（语句不执行）

Change:  PENDING → VALIDATED → SNAPSHOTTED → EXECUTING → SUCCEEDED | FAILED | ABORTED

DirectExec:  EXECUTED | PROMOTED_TO_TICKET(L3) | BLOCKED | SELF_ACKED(L1/L2)
```

## 6. 功能需求

### FR-01 多数据源支持（P0）

**描述**：一套权限/工单/快照/审计体系支持 MySQL（5.7 & 8.0，云托管）、MongoDB、PostgreSQL；新增类型不改核心流程。

**规则**：

- **云托管适配**：
  - 连接需在云控制台将平台出口 IP 加入白名单（K8s egress IP，需固定），此项列入部署清单；
  - 账号体系：每个数据源配置 4 类账号，职责隔离：

| 账号 | 用途 | 最小权限 |
|---|---|---|
| `readonly` | 查询、`EXPLAIN`、结构元数据读取 | `SELECT` |
| `dml` | 执行 `insert/update/delete` | `SELECT,INSERT,UPDATE,DELETE` |
| `ddl` | 执行原生 DDL | `ALTER,CREATE,DROP,INDEX` |
| `onlineddl` | `gh-ost` 专用 | 建表/改表/删表、触发器、`SUPER`（5.7）/`SYSTEM_VARIABLES_ADMIN`+`REPLICATION CLIENT`+`REPLICATION SLAVE`（8.0）、binlog 读取 |

- **能力探测（关键）**：连接建立时探测并落库 `DataSource.capabilities`：

| 探测项 | 5.7 表现 | 8.0 表现 | 平台行为 |
|---|---|---|---|
| `EXPLAIN ANALYZE` | 不支持 | 支持 | 5.7 隐藏该入口，只给 `EXPLAIN` |
| `ALTER ... INSTANT` | 不支持 | 部分支持 | 5.7 一律按 `INPLACE/COPY` 评估锁时长 |
| `gh-ost` 可用性 | 需 `SUPER` + binlog | 需三件套 | **仅在运维为该数据源显式配置了 `onlineddl` 账号且探测通过时可用**；未配置则入口置灰（不降级、不报错），只能走原生 DDL（L3） |
| binlog 是否开启 | 云托管可能关闭 | 同 | 未开则不能做 online DDL，也不能做 binlog 级校验 |
| `max_execution_time` | 仅 SELECT 有效 | 仅 SELECT | 写语句超时靠应用层中断（kill 线程） |

- **版本差异必须显式提示**：界面标注"该库为 MySQL 5.7，不支持 X"，而不是让用户执行后报错；
- 方言解析按目标库版本选择解析器规则（5.7 不支持 CTE、窗口函数、`->>` 等）。

**边界**：
- 连接密码 AES-256-GCM 加密，密钥来自 K8s Secret，任何接口不回显；
- 单数据源写并发固定为 1；
- 连通性巡检独立于业务，失败只告警。

**验收**：
1. 新增一个 5.7 数据源与一个 8.0 数据源，能力探测结果正确，5.7 的 `EXPLAIN ANALYZE` 按钮不存在；
2. 5.7 上提交含 CTE 的 SQL，语法校验直接报"5.7 不支持 WITH 子句"，并给出行号；
3. 云托管实例白名单未加时，连接测试给出明确提示"网络不可达，请确认已加白名单"。

### FR-02 变更前结构快照（默认开启，P0）

**描述**：每次变更执行前自动抓取目标表的**结构快照**。**不备份行数据**（数据量过大，落盘与传输成本不可接受）。

> **这是一次重要的定位变化**：v1.3 及之前，"备份"指的是"把将被改动的行导出来"。v1.4 起，备份只保留**结构**。因此 **DML 不再有数据级回滚能力**，恢复只能依靠①提单人提供的回滚 SQL ②云厂商 binlog 时间点恢复。详见 §16 风险表与 §15 A4。

**规则**：

- 默认勾选；提交时不可取消；可关闭，但关闭后强制升 L3 并记录理由；
- **快照内容**（全部是元数据，KB 级）：

| 对象 | 抓取内容 |
|---|---|
| 表 | `SHOW CREATE TABLE` 原文、列定义、字符集/排序规则、注释 |
| 索引 | 全部索引定义（名称、列序、唯一性、类型） |
| 约束 | 主键、外键、唯一约束、CHECK |
| 触发器 | 全部触发器定义 |
| 分区 | 分区定义与分区列表 |
| 统计 | 表行数、数据大小、索引大小（只读 `information_schema`，不扫表） |
| MongoDB | 集合元数据、索引定义、校验规则、文档数量估算 |

- **抓取时机**：执行前一次，与变更语句在同一会话内顺序执行（`SHOW CREATE TABLE` 不影响事务，无需与 DML 同事务）；
- **用途**：
  1. **结构漂移检测**：执行时比对"提交时的结构指纹"与"当前实际结构"，不一致即中止（防止审核后表被他人改动）；
  2. **回滚方案参考**：审核人/执行人据此判断 `drop`/`truncate`/`alter` 的影响面；
  3. **重建依据**：`drop table` 后可据此重建空表结构（数据仍需另外恢复）；
  4. **审计留证**：变更前后的结构对比，作为变更记录的一部分。
- **存储（本地）**：`/data/snapshot/{system}/{dsId}/{ticketId}/{changeId}/schema.json`（结构化）+ `schema.sql`（原文），单条通常 < 100KB；
- **容量**：全套 OCR 估算 < 20GB（按 5 万次变更 × 200KB × 保留期），PVC 预留 100GB 足够；水位 >80% 告警；
- **保留期**：统一 180 天（结构快照体积小，无需分级）；到期清理前 3 天通知；
- **可见性**：结构快照不含数据，**不敏感**——研发可查看自己工单的快照与前后差异，运维可查看本系统全部；
- **不做的**：不备份行数据、不做 CSV 导出、不做"恢复到临时表"、不做备份文件下载审批（没有敏感数据）。

**边界**：

- 快照抓取失败 → 禁止执行（结构基线缺失会导致漂移检测失效）；
- 表不存在（新建表场景）→ 记录"前置状态为空"，不算失败；
- 视图/存储过程变更 → 抓取对应定义，同上处理。

**验收**：
1. 对 `t_order` 执行 `update`，生成本次变更的结构快照，文件 < 100KB，可查看与上一版的字段差异；
2. 执行前有人给表加了列 → 漂移检测命中，工单中止并提示"结构已漂移：新增列 `remark`"；
3. 快照抓取失败（模拟权限不足）时语句不执行；
4. 磁盘占用增长符合预期（1 万次变更 < 2GB）。

> **对回滚的影响（必须同步告知使用方）**：DML 的回滚 SQL 不再能由系统生成，改为**提单时必填**（FR-08）；`drop`/`truncate` 只能重建空表结构，数据恢复依赖云厂商备份或 binlog。

### FR-03 SQL 收藏与分享（P1）

**规则**：

- 收藏项：标题、语句、目标数据源（可选）、标签、备注、创建人、可见范围；

### FR-04 查询结果与导出（P0）

**规则**：

- 结果缓存：默认 **30 分钟**，最多保留最近 20 次；**导出完成后 5 分钟内清理该结果集**（Q-17）；
- 单次查询结果上限：默认 10 万行 / 50MB，超限截断并提示；
- 研发查询自动追加 `LIMIT 1001`（超出即判定需申请导出）；
- **导出阈值（Q-05）**：
  - ≤1000 行：自助；
  - >1000 行：需运维审批；**上限 100 万行 / 500MB**；
  - **研发申请页与运维审批页都必须展示预估**：行数、预估文件大小、涉及表、是否含大字段；超 50 万行时红字提示"文件较大，建议加条件缩小范围"；
  - 超过 100 万行/500MB → 直接拒绝，提示改用分批或找运维导出。
- 导出格式：
  - `csv`：UTF-8 BOM、首行表头、`NULL` 与空串区分、长数字文本化防科学计数法；
  - `sql`：`INSERT` 语句，含可选 `CREATE TABLE`，每 500 行一块；
  - `txt`：制表符分隔，无表头可选。
- 大文件异步导出，进度可查、可取消，完成后给 24 小时有效的下载链接（本地存储，走应用网关鉴权，不暴露文件路径）。

**验收**：
1. 查询 1500 行时提示需审批，且无法通过分页绕过（每页请求服务端校验）；
2. 审批页展示"1500 行 / 约 2.3MB / 涉及表 t_order"；
3. 申请 120 万行被拒绝并给出上限说明；
4. 导出完成后 5 分钟，结果集缓存被释放（接口返回"结果已过期"）。

### FR-05 历史记录（P0）

- 个人历史：本人查询与工单，含时间、数据源、语句摘要、耗时、状态、风险等级；
- 运维视图：所辖系统全部记录，可按数据源、人员、时间、类型、风险、状态、关键词检索；
- 研发看到的历史**不含**其无权数据源；
- 历史可"再次执行"（重新校验权限与风险；研发的"再次执行"实为"再次查询"）；
- 保留：个人 90 天，审计事件 2 年。

### FR-06 文件导入执行（P1）

**规则**：

- 格式：`.sql`（处理注释、字符串内分号、`DELIMITER`）、`.csv`（生成 `insert`）、`.zip`；
- 上限：50MB / 5000 条语句；
- 解析后**逐条**进入 校验 → 分级 → 结构快照 → 执行 流水线；
- **导入只能由运维发起**（研发无写权限），且同样受风险分级约束；
- **online DDL 支持**：识别 `alter` 并路由到 `onlineddl` 账号（`gh-ost`），进度可见（已拷贝行数、剩余时间、主从延迟）；探测到不支持时该部分语句转原生 DDL 并强制 L3；
- 分批：每 500 条提交一次，失败即停，已成功部分按**提单人提供的回滚 SQL** 逆序回滚（导入不自动生成回滚）；
- 断点续传：从第 N 条继续，需人工确认并重新校验。

**验收**：含 1200 条 `insert` 的文件，第 600 条失败时前 599 条可按回滚 SQL 回退；含 `alter` 时走 `gh-ost` 并显示进度。

### FR-07 定时执行（P1）

**规则**：

- 定时只能设置在**审核通过后**（审核时一并批准计划时间）；
- 支持单次与周期（cron），周期任务需配"最大执行次数 / 结束时间"；
- 时区统一 `Asia/Shanghai`；
- 到点执行前：语法校验 → 风险重算（含窗口判定 +1）→ 精确计数 → 结构漂移检查 → 结构快照 → 执行；
- 风险重算升高（如 L2→L3）→ **中止并回退到待审批**，不自动执行；
- 错过执行时间 > 24h → `EXPIRED`，需重新提交；
- 调度实现（Q-10，K8s、无独立调度器）：应用内调度线程 + **数据库行锁（`SELECT ... FOR UPDATE` 抢占任务）+ 幂等键**（`ticketId+changeId+scheduledAt`），多副本部署不会重复执行；K8s CronJob 每 5 分钟兜底扫描漏跑任务；
- 到点前 10 分钟通知提交人与执行运维，允许取消（仅 `PENDING`）。

**验收**：设 10 分钟后执行 → 到点自动跑；多副本同时运行只执行一次；执行前数据变化导致行数超阈值 → 中止并回退审批。

### FR-08 SQL 上线（变更工单）（P0）

**描述**：研发选择数据库、提交执行 SQL 与回滚方案、选择期望执行时间；审核通过后**研发可自己点击触发执行**（也可由运维执行），定时则到点自动执行。

**规则**：

- 工单必填：系统、模块、数据源（可多选，**仅限同类型**）、语句、变更说明（业务背景）、回滚方案、期望执行时间、结构快照开关（置灰，强制开）；
- **回滚内容**：
  - DML：**回滚 SQL 必填**（系统不再自动生成，因为没有数据备份），提交时做语法校验与"是否命中目标表"的静态检查；
  - DDL：必填**回滚方案**（文本），自动附变更前结构快照；`drop` 额外要求填写"确认不可恢复，将从快照重建表结构"确认语；
- **结构化预览**：解析出"涉及 N 张表、DDL 类型、预估影响行数、是否跨库语句"，供审核人快速判断；
- **审批**：L1/L2 → 运维一级；**L3 → 运维一级 + 组长终审**；提交人不可审自己；
- **执行（关键）**：审核通过后，工单进入"待执行"状态，**研发本人在工单详情页点"执行"即可触发**，也可由运维点执行。执行时：
  1. 前端弹风险确认 → 落 `risk_acknowledged` → 后端校验；
  2. 用该数据源配置的**服务账号**（`dml`/`ddl`/`onlineddl`）执行，研发不接触凭证；
  3. 审计同时记录 `operator=研发A` 与 `exec_identity=dml@ds-123`；
  4. **只能执行工单内已审核的固定语句**——不可改、不可追加、不可换库。
- **结构漂移检查**：执行时比对提交时记录的表结构指纹，不一致则中止并要求重新提交；
- **部分失败**：逐条记录状态，提供"回滚已成功部分"，生成**回滚工单**（见 FR-15）。

**边界**：
- 一单内语句串行执行，不并行；
- 同一数据源同一时刻只允许一个工单执行中；
- 已通过工单不可修改语句，需新建版本，旧单作废；
- 研发触发的执行，若执行时该工单已被撤销/过期，拒绝执行。

**验收**：
1. 研发提交 3 条语句 → 运维一级审 → **（若为 L3 再加组长终审）** → **研发点"执行"成功触发**，界面逐条显示状态与影响行数，审计同时含研发与执行账号；
2. 研发修改工单语句后点执行 → 后端拒绝（语句指纹不匹配）；
3. 研发对写库直接写 SQL（走临时执行）→ 403 且提示"请提交变更工单"；
4. 执行前表结构被改 → 中止并提示"结构已漂移"；
5. DDL 未填回滚方案、DML 未填回滚 SQL → 均无法提交。

### FR-09 风险分级、提醒与升级评审（P0）

见 §7 完整规则。要点：

- 三级：L1 低 / L2 中 / L3 高（L0 只读不参与审批）；
- 分级在**提交时、审核时、执行前**三次计算，取最严格；
- **提醒**：提交页、审核页、执行前各展示一次，均需显式确认并落库（`risk_acknowledged` 事件），无记录则后端拒绝执行；
- **升级**：执行前重算发现等级升高 → 中止，回退审批；
- 阈值可配（全局 / 系统 / 数据源，取最严）；人工只能上调不能下调。

### FR-10 格式与规范校验（P0）

**两层，提交与执行前各跑一次**：

**L1 语法**：按目标库**版本**方言解析（5.7 与 8.0 规则不同），错误给出行号、列号、错误码、原文高亮。

**L2 规范**（可配置，三级 `BLOCK` / `L3强制` / `WARN` / `INFO`）：

| 规则 | 级别 | 说明 |
|---|---|---|
| `drop database` / `drop schema` | BLOCK | 硬禁止，管理员也不可 |
| 多语句拼接（一条语句里多个 `;`） | BLOCK | 必须逐条提交 |
| **`drop table`** | **L3 强制** | 结构不可逆，恢复=快照重建 |
| **`truncate` / `truncate table`** | **L3 强制** | 数据不可逆 |
| **`rename table`** | **L3 强制** | 影响面隐蔽（外键/视图/代码） |
| **`alter table ... drop column`** | **L3 强制** | 列数据永久丢失 |
| **`alter table ... drop index`** | **L3 强制** | 可能引发性能雪崩 |
| **`alter table ... modify` 类型收窄** | **L3 强制** | 静默截断（`varchar(64)` 收窄、`bigint→int`） |
| **`alter table ... convert to charset`** | **L3 强制** | 重建表 + 锁表 |
| **`drop partition`** | **L3 强制** | 整分区数据丢失 |
| `update`/`delete` 无 `where` | **L3 强制** | 不阻断，强制升 L3 + 二次确认 |
| `select *` | WARN | 建议显式列 |
| `select` 无 `limit` 且非聚合 | WARN | 可能拉全表 |
| `like '%x%'` | WARN | 前导通配索引失效 |
| 隐式类型转换 | WARN | 索引失效 |
| `order by rand()` | WARN | 性能 |
| 5.7 语法用在 8.0 库 / 反之 | WARN | 版本兼容提示 |
| 关键字未大写、缩进混乱 | INFO | 仅提示 |

> **口径**：`BLOCK` = 提交阶段直接拒绝，进不到审批；`L3 强制` = 可提交但等级被钉死为 L3，必须组长终审且**不可下调**。两者不混用。
>
> **加粗的 9 条是"结构性破坏"规则**，与 §7.1 的第一行一一对应。它们由代码内置（不是配置项），**即使管理员把阈值调到最宽松也不会降级**——这是防止"配置误改导致 drop 变成 L2"的最后一道锁。

**验收**：
1. `update t set a=1` 提交成功但被迫 L3；
2. `drop database x` 被直接拒绝；
3. **`drop table t_order` / `truncate table t` / `alter table t drop column c` 提交时即被标记 L3**，界面上有红字"结构性破坏，恢复需人工重建"，且无论怎么调阈值都仍是 L3；
4. `select * from t` 带 WARN 并在审核页展示。

### FR-11 性能分析（P1）

**按语句类型隔离手段（安全红线）**：

| 语句 | 允许 |
|---|---|
| `select` / `show` / `desc` | `EXPLAIN`、`EXPLAIN ANALYZE`（仅 8.0；5.7 无此能力时隐藏入口） |
| `update` / `delete` / `insert` | **仅 `EXPLAIN`**，严禁 `EXPLAIN ANALYZE`（后者会真实执行） |
| DDL | 仅静态分析 + 表体积/锁评估；online DDL 额外评估拷贝量、锁时长、主从延迟 |
| MongoDB | `explain("executionStats")`，仅只读 |

**报告内容**：执行计划树、扫描行数/返回行数、是否全表扫描、是否临时表+文件排序、索引使用、锁影响面、对象规模（行数/体积/索引数）、索引建议（只建议不执行）、整体评级（优/良/差）。

**边界**：走 `readonly` 账号、限流、超时 10s 返回部分结果；分析结果随工单留存，执行后可对比"预估 vs 实际"。

**验收**：对 `update` 点分析只出 `EXPLAIN`，用审计+行数校验证明零数据变更。

### FR-12 审计日志（P0）

### FR-15 回滚工单（P1，Q-09）

**描述**：回滚不是一个按钮，而是一张基于原工单的工单。

**规则**：

- 入口：原工单详情页"发起回滚"；
- **预填**：带上**原工单提交时填写的回滚 SQL**（这是唯一来源，系统不会生成）；运维可编辑；
- **必填**：回滚原因（为什么回滚，≥10 字）；
- 继承原工单的：系统、模块、数据源、目标表；
- **审批**：默认一级（原审核人优先，不可自审）；若原单为 L3，回滚同样需组长终审；
- 回滚执行前同样抓结构快照（保证回滚动作本身可追溯）；
- 回滚完成后原工单置 `ROLLED_BACK`，并在原工单时间线留下记录。

**验收**：对一条 `delete` 变更发起回滚，系统带出原单的回滚 SQL（例如 50 条 `insert`），填原因后走审批，执行后数据恢复且原工单标记已回滚。

> **重要边界**：回滚 SQL 由人写，系统**无法验证它是否真的能还原数据**——只能做语法校验和"目标表/字段是否存在"的静态检查。如果原单的回滚 SQL 写错了，回滚会失败或产生新错误。这是"不备份数据"的必然代价，必须在 UI 与培训中讲清。

## 7. 风险分级与审批链

### 7.1 分级表

| 等级 | 判定条件（满足任一） | 研发工单审批链 | 运维临时执行 | 提醒 |
|---|---|---|---|---|
| L0 只读 | `select`/`show`/`desc`/`explain`/`find` | 无需审批（受导出限制） | 直接执行 | 无 |
| L1 低 | 单条 `insert`；`update`/`delete` ≤100 行；`create table`；`alter add column`（可空）；`create index`（普通） | **运维一级** | 弹框自确认 | 提交、审核 |
| L2 中 | `update`/`delete` 101–1000 行；`alter add unique index`；`alter modify column`（非收窄）；批量 `insert` >1000 行 | **运维一级** | 弹框自确认 + 展示影响行数 | 提交、审核、执行前 |
| L3 高 · **结构性破坏**（内置硬规则，不可下调） | `drop table`；`truncate`；`rename table`；`alter drop column`；`alter drop index`；`alter modify` 改类型收窄（`varchar(255)→varchar(64)`、`bigint→int`）；改字符集；`drop partition` | **运维一级 + 组长终审（两级）** + 执行前输入表名确认 | **自动生成工单 → 组长一级审批** | 提交、审核、终审、执行前 |
| L3 高 · **数据影响面** | `update`/`delete` >1000 行；无 `where` 的写操作；**单条语句跨库**；未开结构快照的变更 | **运维一级 + 组长终审（两级）** + 执行前输入确认词 | **自动生成工单 → 组长一级审批** | 提交、审核、终审、执行前 |

> **结构性破坏 DDL 的硬约束（v1.3 新增）**：
> 1. 上表第一行的语句**永远是 L3**，不受风险阈值配置影响，也**不提供任何下调入口**（管理员也没有）；
> 2. 它们**不能被"非窗口期 +1 级"影响**——已经从最高级起算，只会在终审时追加"同意在业务高峰执行"的确认；
> 3. 它们在**运维临时执行通道**中同样走 L3：弹框 → 自动生成工单 → 组长审批，**没有"自确认直接执行"的路径**；
> 4. 执行前必须输入**表名**（不是"确认"二字），输错即中止；
> 5. 结构快照对它们只解决"结构"，不解决"数据"——`drop table` 后可用快照重建空表，**数据必须靠云厂商备份或 binlog**，UI 必须红字写明"此操作不可一键回滚，数据需从备份恢复"。

> **审批深度的最终口径（v1.2 按需求方确认）**：
> - **研发工单**：L1/L2 → **运维一级**；L3 → **运维 + 组长两级**。组长只审 L3。
> - **运维临时执行**：L1/L2 **自确认即执行**（"默认自己同意"）；L3 → 组长一级审批。
> - **不使用四眼原则**：运维执行不设"第二人复核"，也不做"大表强制第二人确认"。安全网是**结构快照 + 必填回滚 SQL + 全量审计**，而不是层层签字。

### 7.2 补充规则

1. 多语句取**最高**等级；
2. 阈值可配（全局/系统/数据源三级取最严）；
3. 人工只能上调，不能下调；
4. **"跨库"的准确定义**：同一条语句引用不同库的对象（`update db1.t1 join db2.t2`、`insert into db2.t select * from db1.t`、MongoDB `$lookup` 跨库）。**一个工单含多个库、多条独立语句不算**——那是常规用法，各库独立快照、独立回滚；
5. **非窗口期 +1 级**（§4.6）：L1→L2，L2→L3；**结构性破坏类 L3 不受影响**（已在最高级），仅追加"同意在业务高峰执行"的终审确认；
6. **执行前重算**：精确计数后发现行数跨档 → 中止，回退审批，不允许"已经批了就继续"。

### 7.3 审批链图示

```
【研发工单】
研发提交 ──> L1/L2 ──> 运维一级审核 ──> 通过 ──> 研发/运维点"执行"
                └─> L3 ──> 运维一级审核 ──> 组长终审 ──> 通过 ──> 研发/运维点"执行"

【运维临时执行】
运维写语句 ──> L0/L1/L2 ──> 弹框自确认 ──> 抓结构快照 ──> 直接执行（记 DirectExecRecord）
           └─> L3 ──> 弹框"需审批" ──> 自动生成工单 ──> 组长一级审批 ──> 通过 ──> 执行

【不做四眼】运维执行不设第二人复核、不做大表二次确认；安全网 = 结构快照 + 必填回滚 SQL + 全量审计
```

### 7.4 风险确认的落地（不可省）

每次"提醒"都必须落一条 `risk_acknowledged`：`{ticketId, stage(submit|review|l3_review|execute), operator, riskSnapshotHash, ip, ua, at}`。
后端在执行前校验"最近一次确认的 `riskSnapshotHash` == 当前风险快照哈希"，不一致（说明风险变了）则要求重新确认。这解决了"弹框关掉就没证据"的问题。

## 8. 关键流程

### 8.1 研发查询

```
研发 → 选系统/模块 → 选数据源（只见库名）→ 写 SQL
  → L1 语法（按库版本）+ L2 规范
  → 服务端权限校验 → 自动 LIMIT 1001
  → readonly 账号执行 → 结果缓存 30min
  → ≤1000 行自助导出 / >1000 行申请审批
  → 导出完成后 5 分钟释放结果集
```

### 8.2 研发变更工单（L1/L2 一级，L3 两级）

```
研发填单（语句 + 回滚方案 + 期望时间）
  → 校验 → 分级 → 提交（风险确认落库）
  → 通知运维
  → 一级：运维审核
  → 若为 L3：二级组长终审（L1/L2 到此结束）
  → 通过
  → 研发点"执行" 或 运维点"执行"（风险确认 → 结构漂移检查 → 精确计数 → 抓结构快照 → 执行）
  → 成功 / 部分失败（可发起回滚工单）
  → 定时单则由调度器到点触发（执行前同样重校验）
```

### 8.3 运维临时执行

```
运维选数据源（读库或写库）→ 写语句 → 校验 → 分级
  → L0：直接执行
  → L1/L2：弹框确认（含快照状态）→ 抓结构快照 → 执行 → 记 DirectExecRecord
  → L3：弹框"需审批"→ 确认 → 自动生成工单 → 组长一级审批 → 通过 → 执行
```

### 8.4 定时执行

```
审核通过（含计划时间）→ 调度器到点（行锁抢占）
  → 重校验（语法/风险/窗口/计数/结构漂移）
  → 风险升高 → 中止回退审批
  → 抓结构快照 → 执行 → 通知
```

## 10. 技术架构约束

### 10.1 控制面 / 执行器分离（为多云预留，一期就做）

```
┌──────────────────────────────────────────┐
│ 控制面（Web + API + 工单 + 权限 + 审计）    │  K8s Deployment，无状态
└───────────────┬──────────────────────────┘
                │ 内部 gRPC/HTTP（mTLS）
┌───────────────▼──────────────────────────┐
│ 执行器 Executor（每朵云 / 每个网络域一个）  │  有状态，持有数据库凭证
│  - 连接池、执行队列（按数据源串行）        │
│  - 结构快照落本地 PVC                      │
│  - gh-ost 进程管理                         │
│  - 能力探测                                │
└───────────────┬──────────────────────────┘
                │ 私网
          ┌─────▼─────┐
          │ 云数据库   │
          └───────────┘
```

**理由（Q-10）**：后期涉及多个云，若把执行逻辑写在 Web 里，多云就要复制整套应用。一期就拆开，后期只加执行器，前端不动。
**一期部署**：控制面 2 副本 + 执行器 2 副本（同一 K8s 集群），执行器通过云内网访问数据库。

### 10.2 数据源适配器接口

```java
interface DataSourceAdapter {
  ProbeResult probe(ConnConfig c);                  // 版本、权限、binlog、能力
  ParseResult parse(String stmt, DbVersion v);      // 版本相关方言
  StatementKind classify(String stmt);              // SELECT|DML|DDL_*
  Plan explain(String stmt);
  long countAffected(String stmt, Tx tx);           // 精确，事务内
  SnapshotRef snapshot(SchemaScope scope);          // 结构快照，非事务
  ExecResult execute(String stmt, Tx tx);
  DdlStrategy ddlStrategy(DdlStatement ddl);        // NATIVE|GH_OST|VENDOR
  Schema describe(String table);
}
```

### 10.3 关键实现约束

1. 执行器按数据源串行，每数据源一个队列；
2. 结构快照在变更执行前抓取（同会话、顺序执行，不进事务），快照失败即中止；
3. `gh-ost` 独立进程，进度从 `_ghc` 表或日志解析；失败可 `--resume`；
4. 调度：DB 行锁抢占 + 幂等键 + K8s CronJob 兜底；
5. 大文件流式写 PVC，不进 JVM 堆；
6. 风险规则 DSL 化（YAML：条件 + 等级 + 文案），支持热更新；
7. **能力不可用则 UI 隐藏**，不让用户执行后才发现不支持。

## 11. 边界与异常

| 场景 | 处理 |
|---|---|
| 结构快照失败 | 不执行，工单置"快照失败"，可重试 |
| 执行器宕机 | 已提交批次保留；重启后进入"需人工确认"，不自动续跑 |
| `gh-ost` 中断 | 支持续跑，进度从元数据恢复 |
| 主从延迟 > 30s | DDL 排队等待 |
| 连接失败 | 工单保持 `APPROVED`，可重试；连续 3 次失败通知运维 |
| 结构漂移 | 中止，要求重新提交 |

## 15. 遗留假设（4 条，均不影响开工）

**A1. 组长缺位时 L3 怎么兜底？**
我的处理：系统建档时校验"该系统的运维必须至少有一名上级组长"，否则**拒绝建档**；运行期组长离职导致无人覆盖时，该系统 **L3 工单不可提交**（提交即拦截并提示），避免工单卡在半路。
→ 如果你希望"无人覆盖时自动落给管理员终审"，告诉我，改一行路由即可。

**A2. `gh-ost` 单独账号的权限实测**
按你的要求：**online DDL 只在运维为该数据源配置了独立的 `onlineddl` 账号后才可用**，未配置则入口置灰（不降级、不报错）。账号需要 `SUPER`(5.7) / `SYSTEM_VARIABLES_ADMIN + REPLICATION CLIENT + REPLICATION SLAVE`(8.0) 以及 binlog 读取权限。
→ 建议开工前拿一个 8.0 实例实跑一次，确认云托管上这些权限可授予。

**A3. 多个组长覆盖同一系统时的终审方式**
我按**或签**（任一组长批即可）设计，并记录实际审批人。
→ 若需要会签（所有组长都要批），改动在审批引擎，不影响其他模块。

**A4. 不备份数据后的兜底，是否要接 binlog 解析？**
现状：DML 没有数据快照，误改后的恢复路径只有两条——①提单人写的回滚 SQL（依赖人写对）②云厂商 binlog 时间点恢复（粒度粗、要停服或恢复到新实例比对）。
→ 建议 P2 加一个"binlog 回滚建议"：用 `binlog2sql`/`my2sql` 解析 undo，自动生成反向 SQL 供人确认。这能补上最大的一块空缺，但需要 binlog 可用（云托管通常有）与额外解析服务。**一期不做，仅确认方向。**

> 已解决的历史假设：研发 `select` 是否要审批（→ 只读库自助）；研发 L1/L2 是否两级（→ 只运维一级）；组长是否按系统单独授权（→ 由组员权限自动继承，见 §4.7）。

## 16. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **DML 无数据备份，误 update/delete 不可自动回滚**（v1.4 引入） | 改错的数据无法从平台恢复 | ①提单必填回滚 SQL（提交时静态校验）②执行前展示影响行数/表占比红字警告 ③依赖云厂商 binlog PITR ④P2 接 binlog 逆向解析（§15 A4）。**这是本期最大的已知风险，需业务方明确接受** |
| 回滚 SQL 由人写，可能写错 | 回滚失败或改出新错误 | 提交时语法 + 目标表/字段存在性静态校验；回滚工单二级确认；回滚本身也抓结构快照 |
| 本地结构快照与库同机房 | 机房故障时快照丢失 | 快照只有结构、可重新抓取，影响可控；灾难恢复依赖云厂商 |
| 5.7 缺少 `EXPLAIN ANALYZE` | 性能分析精度下降 | 5.7 用 `EXPLAIN` + `SHOW STATUS` 近似；显式标注"估算值" |
| 云托管 `SUPER` 缺失 | online DDL 不可用 | 入口置灰，只能走原生 DDL（L3）；由运维显式配置独立 `gh-ost` 账号后才开放 |
| 运维临时执行绕过审批 | 治理失效 | L3 强制生成工单交组长；`direct_exec` 月度统计；超阈值通报 |
| **运维执行无第二人复核**（已确认接受） | 手滑/误判时无人拦截 | 结构快照 + 回滚 SQL 必填 + 全量审计；L3 由组长把关；月度抽检 `direct_exec`；执行前红字展示影响行数与表占比 |
| 组长缺位导致 L3 无法终审 | 工单卡住 | 建档时强制校验运维有上级组长；运行期无人覆盖时 L3 提交即拦截并提示（§4.7） |
| 审批人瓶颈 | L3 排队 | 每系统配 ≥2 名运维；组长 ≥1；SLA 监控 |
| 磁盘写满 | 全部变更停止 | 水位告警 + 自动清理 + 容量预估 |
